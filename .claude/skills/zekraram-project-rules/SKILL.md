# قوانین ثابت پروژه «ذکرآرام»

این فایل، حافظه‌ی بلندمدت پروژه است. کاربر دانش برنامه‌نویسی ندارد و نمی‌تواند
اشتباهات فنی را خودش تشخیص دهد — پس بار تضمین کیفیت کاملاً روی توست.

---

## ۱. معماری و محدودیت‌های قطعی

- استک: React 19 + TypeScript + Vite + Tailwind CSS
- ساختار فولدر: هر قابلیت = یک فولدر زیر `src/features/`
- **هیچ سرور بک‌اندی وجود ندارد و نباید اضافه شود** — همه‌چیز client-side
- ذخیره‌سازی: `localStorage` + پشتیبان همزمان در `IndexedDB`
- تاریخچه **نامحدود** است — هیچ‌جا نباید داده‌های قدیمی trim شوند
- هدف نهایی: تبدیل به اپ اندروید با Capacitor → انتشار در کافه‌بازار/مایکت/گوگل‌پلی
- **فقط از Web APIهای استاندارد استفاده کن** (Notification API، Wake Lock API،
  Web Share API، navigator.vibrate). هیچ چیزی که فقط روی مرورگر دسکتاپ کار کند
  قابل قبول نیست — این اپ فقط روی موبایل اندروید استفاده می‌شود.

## ۲. باگ‌های شناخته‌شده که هرگز نباید تکرار شوند

| باگ | قانون |
|---|---|
| مربع سفید در تور آموزشی روی گوشی‌های شیائومی | افکت spotlight فقط با CSS استاندارد (`position: absolute` + `z-index` + `box-shadow`). هرگز canvas یا `clip-path` پیچیده |
| CSS سراسری که Tailwind را override می‌کند | قبل از اضافه کردن کلاس در `index.css`، مطمئن شو با utility class همان المان تداخل ندارد (این باگ قبلاً هر ۵ مرحله‌ی تور را همزمان خراب کرده بود) |
| باگ برچسب «ویژه مشترکین» زودهنگام | همه‌ی نقاط قفل‌شونده **باید** از hook مشترک `useTrialGate` استفاده کنند، نه منطق جداگانه |
| ویبره‌ای که حس نمی‌شود | مدت ویبره باید به‌قدری باشد که موتور ویبره‌ی گوشی واقعاً حسش کند و سه شدت از هم قابل تفکیک باشند |
| محاسبه‌ی چرخه با timestamp دقیق | مقایسه‌ی روزها همیشه در سطح «روز تقویمی» باشد، نه میلی‌ثانیه |

## ۳. قوانین طراحی ظاهری (تخطی‌ناپذیر)

- **RTL کامل** با `dir="rtl"` و فونت فارسی (Vazirmatn)
- **رنگ ثابت دکمه‌ها/آیکون‌ها/هایلایت‌ها**: سبز پررنگ و غنی — این رنگ **مستقل** از
  پالت پس‌زمینه است و با تغییر تم کاربر عوض نمی‌شود
- **پالت پس‌زمینه**: دقیقاً ۶ رنگ (سبز ملایم پیش‌فرض، زرد/کرمی، طوسی، یاسی،
  آبی کم‌رنگ، صورتی). این را با رنگ ثابت بالا اشتباه نگیر
- اپ در **حالت روز (Light Mode)** شروع می‌شود
- ریسپانسیو کامل موبایل و تبلت اندروید
- **هیچ عنصری نباید بیرون از ناحیه‌ی دید صفحه بیفتد** — پیام‌ها، toastها، و
  مودال‌ها باید همیشه داخل viewport موبایل قابل مشاهده باشند

## ۴. قوانین مربوط به متن پیام‌ها

- **متن‌ها باید کلمه‌به‌کلمه پیاده شوند، نه بازنویسی مفهومی.** در دورهای قبلی،
  متن‌های تعیین‌شده با نسخه‌های «شبیه» جایگزین شده بودند که اشتباه بود
- قیمت‌ها همیشه با فرمت «۶۰ هزار تومان»، هرگز «۶۰۰۰۰ تومان»
- عبارت زمان باقی‌مانده، **در همه‌جای اپ یکسان**: روز اول «۳۰ روز رایگانه»،
  روزهای بعد «[عدد] روز دیگه رایگانه»
- کلمه‌ی فنی «JSON» هیچ‌جا به کاربر نشان داده نشود — همه‌جا «فایل پشتیبان»
- اگر پیام/toast جدیدی در کد پیدا کردی که در سند تصمیمات نیست، **خودت تغییرش نده** —
  در گزارش نهایی جداگانه فهرست کن تا کاربر تأیید یا اصلاح کند

## ۵. مدل اشتراک (خلاصه‌ی قطعی)

**دوره‌ی آزمایشی**: ۳۰ روز از اولین اجرا، همه‌چیز رایگان.

**قفل‌شونده بعد از ۳۰ روز**: تسبیحات اربعه و حضرت زهرا (س) · «ریزآمار روزهای
گذشته» (کامل) · دفترچه‌ی کارهای خوب (کامل) · تغییر رنگ‌بندی و حالت شب/روز ·
ذکر چندمرحله‌ای دلخواه (ساخت + استفاده) · حذف تبلیغات · ویجت خانه

**همیشه رایگان (هرگز قفل نمی‌شوند)**: بکاپ‌گیری · Wake Lock · تقویم مناسبت‌های
مذهبی · ذکر دلخواه تک‌مرحله‌ای (تا ۷ مورد) · سیستم ستاره و مدال

**نکته‌ی مهم امنیتی**: قفل شدن «ذکر چندمرحله‌ای دلخواه» عمدی است تا کاربر نتواند
با ساخت دستی یک ذکر مشابه تسبیحات اربعه، قفل آن را دور بزند.

پرداخت واقعی هنوز وصل نیست — فقط فلگ محلی `isProUser`.

## ۶. استاندارد تست (مهم‌ترین بخش)

کاربر برنامه‌نویس نیست و فقط روی گوشی واقعی تست می‌کند. پس قبل از تحویل:

1. `build` و `type-check` باید تمیز پاس شوند
2. **با Playwright در viewport موبایل تست کن** (نه دسکتاپ) — عرض حدود ۳۹۰px
3. برای هر تغییر بصری، **اسکرین‌شات بگیر و مختصات واقعی المان‌ها را بررسی کن** —
   نه صرفاً «به‌نظر درست است». در دور قبل، گزارش «فقط یک مرحله کمی جابه‌جاست»
   داده شد در حالی که هر ۵ مرحله خراب بودند
4. برای هر مورد اصلاحی، **جدا و به‌تفکیک** گزارش بده که چطور تأیید شد — نه یک
   جمله‌ی کلی برای همه
5. اگر چیزی را نتوانستی در محیط تست تأیید کنی (مثل دانلود فایل یا Web Share API که
   در سندباکس محدود است)، **صریح بگو تست نشده** — گزارش موفقیت جعلی نده

## ۷. نحوه‌ی گزارش به کاربر

- خلاصه‌ی **ساده و کاملاً غیرفنی** بنویس (کاربر دانش فنی ندارد)
- مشخص کن کدام موارد کامل تست شدند و کدام نیاز به بررسی دستی کاربر روی گوشی دارند
- اگر تصمیمی گرفتی که در پرامپت مشخص نشده بود، کوتاه توضیح بده چرا
- اگر به مشکلی برخوردی که نیاز به تصمیم کاربر دارد، **فرض نکن — بپرس**
- در پایان یک Pull Request جدید بساز
